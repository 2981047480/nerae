# P02-10 Android transport worktree evidence

Status: **partial**. This isolated worktree now contains an Android HTTPS transport implementation and reproducible source/JVM probes. It is not integrated, linked into an application, packaged as an APK, or tested on Android runtime/device.

## Implementation boundary

- `apps/client/src/uni_modules/nerae-https/utssdk/app-android/` implements the existing callback `request`/`cancel` surface and `headersJson` wire shape. It accepts HTTPS only, GET/POST only, bounded string request bodies and timeouts, an allowlist of request headers, and restricted RFC 3986 path/query characters.
- The transport uses `SSLSocketFactory.getDefault()`, sets HTTPS endpoint identification before handshake, and performs one HTTP/1.1 exchange over that TLS socket. It does not call `CookieHandler`, use a cache, follow redirects, retry, or log request/response material. It sends `Connection: close`, `Accept-Encoding: identity`, and `Cache-Control: no-store`.
- Response parsing is bounded by line/header/chunk/body limits. It rejects duplicate headers, conflicting or repeated Content-Length, Transfer-Encoding plus Content-Length, non-identity content encoding, unsupported transfer framing, invalid/truncated chunks, malformed UTF-8, and invalid response lines. Response headers are restricted to a small allowlist before returning `headersJson`.
- The Android UTS callback bridge posts through `Handler(Looper.getMainLooper())`; worker and timer executors are separate. Timeout starts at request submission, includes worker queue delay, and best-effort cancels the submitted future as well as closing the active socket. Timeout text is passed separately by UTS and checked against the strictly parsed request envelope. Scheduler or worker rejection settles as a fixed `unavailable` error and removes the active slot. Registry settlement is guarded by an atomic one-shot flag. The main-looper behavior is source-level only; it was not run on Android.

## Verification

- `bash docs/evidence/P02/P02-10/verify-android-transport.sh` — **exit 0** with the approved local loopback run. It compiled the production Kotlin sources and synthetic test using Corretto 17, Kotlin 1.9.24, and Android API 35 `android.jar`, then ran an isolated JVM HTTPS harness. The only servers bound were to `127.0.0.1`; the test-only PKCS#12 trust store was passed to that JVM process and did not modify system trust.
- The loopback harness verified trusted local TLS success; an untrusted CA and wrong hostname fail; redirects (same-origin, cross-origin, and HTTPS-to-HTTP) are returned without a second request; fixed-length, chunked, and EOF-delimited bodies; the 4 MiB boundary and overflow; malformed status/header/framing/chunk/truncation/encoding rejection; request method/header/path/size rejection; timeout and cancellation; and at-most-once callback delivery through an injected synthetic callback executor.
- The queue regression occupies a single worker before request submission, confirms the queued request times out before the worker is released, confirms an additional request is rejected at the concurrency cap, and verifies timed-out tasks do not reach the loopback server after the worker is released. Separate reject-once scheduler and worker fixtures verify that each rejection returns `unavailable`, cleans the active slot, and allows a subsequent request to succeed.
- Timeout normalization was checked against generated Kotlin: the wrapper requires an integer in range and emits `"" + _request.timeoutMs.toInt()`. A JVM synthetic check passed with `Number` values `1000.0` and `120000.0`, producing exactly `"1000"` and `"120000"`. The native parser accepted equivalent JSON numeric forms `1000.0` and `1.2e5`, matched them to those canonical timeout strings, and rejected `1000.5` and an extreme exponent. HBuilderX UTS conversion confirms the generated expression; the DCloud JS-to-Kotlin runtime itself was not executed.
- The test installs a process-local `CookieManager`, confirms a received `Set-Cookie` is not retained or sent on a later request, and confirms production code did not replace the process `CookieHandler`. The production bridge itself does not use that API.
- A normal-sandbox run of the same script failed before tests because loopback bind returned `PermissionError: Operation not permitted`; that failure scene is retained at `/private/tmp/nerae-p02-10-android-tls.q5iYEe6K`. The approved local-only rerun passed and cleaned only its own successful temporary directory.
- `bash docs/evidence/P02/P02-10/verify-android-uts.sh` — **exit 0**. HBuilderX 5.33 converted the module UTS wrapper to Kotlin and emitted the production Kotlin sources in its disposable output. The generated wrapper validates and normalizes timeout values, passes `timeoutMsText` to the native request bridge, and retains the cancel call. This is UTS source conversion, not a full Android app link/build.
- `git diff --check` — **exit 0**.

## Remaining limits and risks

- The transport uses a hand-written HTTP/1.1 parser over `SSLSocket`. The strict framing checks have synthetic loopback coverage, but the parser needs independent security review and real Android interoperability testing before integration.
- The JVM test uses JSSE's default socket implementation with a test-only trust store override. It confirms certificate-chain and hostname-verification behavior in that JVM process; it does not establish Android Conscrypt behavior, device system roots, Android lifecycle behavior, or actual UTS callback delivery on the main Looper.
- HBuilderX generated the UTS Kotlin wrapper, but the generated wrapper was not fully linked against the Android app's DCloud runtime. No uni-app Android resource build, APK/AAB, installation, emulator, or device test was performed.
- No authentication or workout caller is connected. Callers still must parse and validate the returned `headersJson` and response body against their own schema. No production endpoint was contacted.
- Ordinary sandbox loopback was denied; the successful harness required the task-scoped authorization for local-only binding. The scripts are invoked with `bash` because changing executable file modes was denied by the filesystem.
