# K01-02 · 跨设备训练顺序合同增补

状态：partial，未接受；基线 `40d4b72`。本项是尚未发布的合同修订，不能单独证明或交付跨设备同步。Lead 负责合同收口，独立 reviewer 只读审核。

问题：当前持久化快照按 map 返回，既没有动作条目的完整顺序，也不能以每个动作内部的 setIndex 推断不同动作的顺序。新增每次组批次/读详情的完整 `exerciseEntryKeys`，按变更后全部实际组所属条目校验精确集合及顺序；允许仅排序，版本冲突不覆盖；条目内实际组 setIndex 必须唯一。最后一组删除时移除条目，显式恢复须提供完整组并重新指定位置。2000 条目是技术上限。训练后保存确认完整输入，逐组模式须逐组确认；空白及未确认草稿不冒充实际组，需要独立的跨端草稿机制。普通详情不保留已删除组值，因此跨设备不能假称能够直接撤销；有可恢复快照的设备可按原合同显式恢复。

本地静态合同检查 99 项通过；在临时目录以固定 `openapi-typescript 7.6.1`、Go 生成器和 schema 验证器运行 `api/tests/codegen/check.sh` 通过；任务图检查通过。静态 schema 只能检查字段/数组形状，无法证明顺序集合恰好与服务器变更后的实际组一致、组内索引唯一或事务原子性。必须由服务端运行时负例覆盖这些规则，并测试旧版本、并发、删除/恢复和失败回滚。

独立审核指出当前客户端请求不提供新必填顺序、读取也不验证该字段；服务端领域与数据库尚无顺序实现；逐组模式的最终保存当前可能把未确认行一并送出。以上均为实现阻塞，本合同不得与旧消费者混合视为可用；必须在同一集成版本更新生成代码、客户端、服务端及迁移，并重新验证。旧数据库若有实际组但无可靠顺序，迁移前必须停止并制定恢复路径，不凭数据库自然顺序回填。

真实 HTTP、用户设备、账户隔离、离线重试、草稿跨端保存和 iOS/小程序/Android 端到端均尚未验证。本证据不改变 K01、U02、A04 或 P02 的接受状态。
