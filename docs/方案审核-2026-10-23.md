## 3. 发现与最小修正

### R01 · P1 · 训练内容缺少可读取的动作说明，动作库也没有交付给客户端的约定

**证据**：[PRD 计划详情](/Users/zephyr/Documents/项目/nerae/docs/PRD.md:335)要求动作名、要点和替代动作；[TrainingDay](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:5597)的 items 却复用 [PrescriptionInput](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:6506)，只有 exerciseId、组次及备注等字段，没有动作名称、要点或冻结快照。扫描全部操作未找到动作库读取接口。ER 已要求保存 [exercise_snapshot](/Users/zephyr/Documents/项目/nerae/docs/数据模型与ER设计.md:256)，但 API 未投影它。

**触发与影响**：新设备打开训练计划时能得到动作 ID，却没有已定义的数据来源显示动作名称和教学提示；自由训练与手动编排也缺少选动作的数据来源。若临时按最新字典补全，又会违背旧计划冻结动作说明的约定。

**静态复现**：仅含 ID 的动作项通过；向训练日读模型加入 `exerciseSnapshot` 被 `additionalProperties: false` 拒绝。该字段名只是探针示例，问题是当前白名单中不存在任何等价快照字段。

**最小修正**：拆分动作写模型和读模型，读模型返回所用版本的名称、要点及必要提示。动作选择可用只读接口，也可交付明确版本的客户端字典；必须明确同步和下架规则，不要求为了此事先做完整内容后台。

**验收**：清空客户端缓存后仍能显示计划动作；动作库改名/停用后，历史计划说明不变；新建时能选择当前可用动作。

### R02 · P1 · 教练草稿没有明确的重新读取入口

**证据**：[教练计划资源](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:4306)只有 PUT；[关系计划列表](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:4413)定义为已发布计划；学员 `/me/plans/{id}` 明确投影已发布版。ER 要求[教练看到最新内容头与 publishedVersion](/Users/zephyr/Documents/项目/nerae/docs/数据模型与ER设计.md:264)，但未明确相应读取契约。

`GET /coach/students/{relationId}` 的成功响应仍是[任意 object](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:705)，没有声明包含草稿或其完整字段，因此不能据此认为回读问题已经解决。

**触发与影响**：教练生成或保存未发布草稿后退出，次日继续编辑，或另一设备遇到 412 后需要读取最新版本，当前契约没有明确可用的操作。仅依赖上一笔写响应或本地缓存不能支持这一过程。

**最小修正**：补教练自己的草稿列表/详情读取，或者明确一个既有读取操作的教练投影；返回当前版、已发布版和可编辑状态。将学员详情改为具名分区读模型，明确各授权范围可见字段及缺权限的状态。

**验收**：保存→退出→重进能继续原草稿；跨设备冲突后可重新读取；学员始终只能看到已发布版本。任意 object 接受空对象或伤病字段的探针只证明 schema 无约束，不证明服务实际泄露数据。

### R03 · P1 · “今日训练”和“未训练提醒”缺少日历与执行进度规则

**证据**：[PRD 今日待办](/Users/zephyr/Documents/项目/nerae/docs/PRD.md:551)要求判断“连续 2 天计划日未完成”，[首页](/Users/zephyr/Documents/项目/nerae/docs/PRD.md:891)展示今日训练。模型中的 [plan/plan_day](/Users/zephyr/Documents/项目/nerae/docs/数据模型与ER设计.md:253)只有内容版本及 weekIndex/dayIndex，没有明确计划启用日期、当前执行计划、暂停/顺延或日期映射规则。会话日期记录的是已经发生的训练，不能自动定义原本应该发生的训练。

**触发与影响**：学员周四另存一个四周计划，周五应该执行哪一天？同时另存两套计划时选哪套？漏练后顺延还是跳过？如果客户端、待办任务和统计各自推断，会产生不同的“未完成”、完成率和今日内容。

**最小修正**：明确内容周期与执行安排分离，定义当前计划、开始锚点/时区、执行进度、跳过与改期的语义。是否采用固定日历或顺序推进应作为产品决定；App 应根据已有可训练时间给默认安排，用户只改例外。无需因此建设复杂日历系统。

**验收**：周中开始、休息日、漏练、切换计划、时区变化、离线补录和计划改版都产生唯一可解释结果；历史记录不被重新归日。

### R04 · P1 · 服务关系内缺少学员回复路径

**证据**：[关系创建](/Users/zephyr/Documents/项目/nerae/docs/数据模型与ER设计.md:184)允许没有 appointment；[点评发送](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:4465)仅限教练，且须关联计划或训练。唯一消息资源是 `/appointments/{id}/messages`。ER 已明确[关系聊天只预留模型](/Users/zephyr/Documents/项目/nerae/docs/数据模型与ER设计.md:378)，不是已交付 API。

**触发与影响**：教练带入一个没有咨询单的已有学员，发布计划并点评后，学员无法通过该关系提出问题或回复；尚未创建计划的新学员也没有通用关系消息入口。督促/续费文案有生成接口，却缺少不强绑训练记录的发送路径。

**最小修正**：提供以服务关系为边界的最小双向文字会话，或定义同等可用的回复机制；定义发送资格、未读/通知、结束后的只读状态与健康引用权限。保留咨询和关系的独立访问边界。

**验收**：没有 appointment 的有效关系也能双向交流；未创建计划时可询问；结束关系后的行为符合保留政策；无关教练不能访问，撤权不能通过消息摘要被绕过。

### R05 · P1 · 教练 AI 草稿的成功与失败响应不自洽

**证据**：[CoachAiDraftResponse](/Users/zephyr/Documents/项目/nerae/api/openapi.yaml:7974)对所有状态强制 planId/planVersion，但 content 对 `ready` 也不是必填。说明同时要求信息不足或安全阻断时省略正文。

**静态复现**：

| 响应样例 | 当前 schema 结果 | 问题 |
|---|---|---|
| `ready` + planId/planVersion/aiRunId/warnings，缺 content | 接受 | 不能保证返回可供审阅的草稿内容 |
| `needs_input` + aiRunId/warnings，没有计划 | 拒绝 | 尚未生成计划时，无法只返回真实的待补信息结果 |
| `safety_block` + aiRunId/warnings，没有计划 | 拒绝 | 被阻断也必须引用一个计划版本，而其创建规则未定义 |

现有 ER 要求计划版本具备完整内容快照，未定义这里的“无正文计划版本”生命周期。不能靠伪造 ID 或空正文补齐必填字段。

**最小修正**：按状态定义互斥响应：ready 必须能取得完整草稿与版本；needs_input/safety_block 可只有真实 aiRunId、缺项或原因。若要持久化不完整工作稿，明确独立草稿实体及其与正式计划的转换，不隐式占用正式版本。

**验收**：首次生成时的信息不足/安全阻断不产生假计划；ready 缺正文的反例被拒绝；重试和重新编辑仍能追溯同一工作过程。已有发布助手的状态修复不能自动代表教练生成接口也已覆盖。

### R06 · P1（陌生获客试点）· 站内咨询到平台外成交仍缺可执行路径

**证据**：[PRD 核心循环](/Users/zephyr/Documents/项目/nerae/docs/PRD.md:90)依赖平台外成交；[通信规则](/Users/zephyr/Documents/项目/nerae/docs/PRD.md:612)又禁止在小程序内展示个人微信号、二维码和外部支付链接，且注明平台规则待核实。文档没有定义陌生双方如何完成后续联系与交易安排。

**触发与影响**：原本互不认识的学员与教练在站内谈妥后，下一步操作不明确。如果试点只使用教练已经认识的私域学员，交付可能成立，但无法证明“平台为教练带来新客户”。

**最小修正**：先核定一种平台允许的联系与后续安排方式，并把学员和教练双方操作写到流程里，包括未读、拒绝通知授权、未达成服务和重新联系。此处不建议绕过平台规则，也不要求改变已确认的不收款方向。

**验收**：由两名此前没有联系方式的测试参与者走通“选择教练→咨询→后续安排→同一服务说明确认”；另按自然广场、免费计划转入、教练自带三组报告结果。自带学员的交付数据不替代新增获客证据。

**核验边界**：微信官方客服/订阅消息页面本次无法读取，域名限定检索也没有结果；没有据此确认任何站外联系政策。应取得适用于实际业务类目的官方答复或实际提审结果，不能把历史审查中的规则引用当成本次最新核验。

**压力情景，不是实际用量预测**：假设每次问答 3,000 个未缓存输入 token、500 个计费输出 token，每次 0.004 元；若每日使用 10 次、30 天为 1.2 元，仅问答就超过 PRD 免费学员 0.5 元/月的目标。这不证明平均用户一定超支，说明“每日次数额度”不足以保证成本目标，还需实际使用分布、token 上限、历史截断、缓存、重试及费用熔断。

**最小修正与验收**：统一试点/正常使用/配额高使用三档，列启用时间、流量假设、审核人力和外部费用；区分平均与高使用成本。用真实供应商测试记录 token 和延迟；仅批准明确配置下的模型及失败路径。普通业务接口与 AI 生成的延迟目标分别定义，当前 P95 ≤500ms 不应未经验证套给同步生成全部正文的请求。

## 4. 产品判断与下一步顺序

产品值得继续验证的价值是：学员更快开始并坚持训练，教练更省力地持续交付。平台外收款与不抽佣是已确认的边界，尚不能单独证明用户会迁移或教练会持续使用。建议保持方向，通过以下顺序降低返工：

| 顺序 | 具体交付 | 用户需要判断什么 | 完成证据 |
|---|---|---|---|
| 1 | 修复 R01–R05；明确今日训练、回读和双向回复；同步 R07、R10 的当前口径 | 执行安排的默认规则；尚未确定的联系方式 | 更新后的流程/契约和对应反例通过 |
| 2 | 制作两条最小交互路径：学员开始并完成训练；教练继续草稿、发布并回复 | 默认下一步是否符合真实工作习惯 | 含首次/重复/空数据/错误/撤权状态的可操作原型；动作预算实测 |
| 3 | 实现一个完整交付闭环 | 对真实交付结果作验收 | 登录→双方确认关系→授权→草稿→发布→训练→双向反馈；重启、弱网、撤权、重复请求均验证 |
| 4 | 单独验证 R06 的陌生获客路径，再推进已定义的 P0-B | 免费层是否带来使用与有效咨询；是否值得扩供给 | 来源分组后的试点数据、真实运营处理记录、成熟观察窗 |

这是一份实施顺序建议，不是擅自修改 P0-A/P0-B 或冻结新范围。可先用教练自带学员测试交付，但要清楚其验证不到陌生获客和免费转化。
