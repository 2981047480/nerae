# Nerae A 方案复核报告

> 复核日期：2026-10-22；对象：[PRD v1.3](<docs/PRD.md>)。
> 性质：方案审查与修订建议，不是法律意见、医学认证或开发完成报告。
> 变更边界：本次不修改原 PRD、成本清单或用户已确认的业务决定。
> 模型说明：Lead 主审，另启动一个默认运行时子代理独立复核。当前委派接口不提供模型选择参数，未能指定或确认 Super Bunny，不能将本轮独立审查称为 Super Bunny 审查。

## 一、结论

**A 方案可以继续，但当前 PRD 不应视为已完成开发评审，更不能据此承诺公开上线时间与全部合规成本。** 可以做低风险原型；真实健康数据试点前必须关闭下文的阻塞项。

保留用户已确认的方向：
- 自由教练自主定价，学员在教练广场选择。
- 线上指导、训练记录、教练反馈与 AI 能力。
- A 阶段不在平台内收款、不代收教练服务费、不做分账。

需要撤回或改正此前表述：
1. **不收款不等于不需要相关许可、网络安全义务或平台责任。** 当前材料不足以排除 EDI/ICP 许可证/等保适用性；也不能反过来断言一定需要。应按实际业务、经营主体与主管部门口径确认。
2. **“58% 的 AI 训练计划不安全”是统计口径错误。** 引用综述的 58% 指纳入研究中 14/24 项报告安全问题，不是所有生成计划的错误率。
3. **高回填率不能证明成交真实；30 秒不能约束专业判断。** 两项都不应原样作为硬性发版条件。

## 三、详细发现

### R01｜阻塞｜AI 审核边界和安全失败处理互相冲突

**证据**：[PRD:247–264](<docs/PRD.md#L247-L264>)、[PRD:390–417](<docs/PRD.md#L390-L417>)。

- 一处写“任何计划必须三道闸门”，另一处允许免费 AI 计划不经教练确认直接展示。用户身份/是否付费不是训练风险分层依据。
- “任一闸门失败就降级模板”未区分技术失败和安全失败。识别到疼痛、疾病、禁忌或资料不足时，不应继续推荐通用训练模板。
- 每周 10%/20% 增量等参数没有来源与适用人群，不能以 JSON 校验成功作为生理安全证明。
- 单一关键词拦截不能代替风险识别、缺失信息处理与有资质人员审查。

**最小修正建议**：
1. 明确两条产品路径：教练服务中的个性化计划须人工确认；学员自助功能另有明确的适用人群、内容来源与限制，不能声称同样经过三重审核。
2. 推荐首版：AI 先做教练计划/反馈草稿；无教练学员使用专业人员预审的基础模板与记录解释，暂不自动给出个性化加重方案。此项需要用户确认，不视为已变更需求。
3. 把结果分为 `技术失败`、`信息不足`、`安全阻断`、`待人工审核`、`可发布`；只有纯技术失败且风险筛查通过时，才允许采用已审核模板。
4. 建立成人/目标人群范围、专业规则审核人、版本、回归用例与紧急停用开关；免责声明不能替代这些控制。

**验收**：疼痛/风险输入不得进入模板兜底；未审核草稿不得变成正式计划；发布后再次修改需重新审核；按角色和风险状态逐项测试。

### R02｜阻塞｜健康数据授权与教练访问权限没有形成闭环

**证据**：[PRD:236–245](<docs/PRD.md#L236-L245>)、[PRD:359–364](<docs/PRD.md#L359-L364>)、[PRD:473–484](<docs/PRD.md#L473-L484>)、[PRD:728–743](<docs/PRD.md#L728-L743>)。

文档收集伤病史、身体数据和照片，允许扫码默认绑定、导出学员信息；但没有明确：谁能看哪类数据、学员如何授权、解绑/更换教练后如何收回权限、AI 提供商收到什么数据。加密和一句“最小权限”不足以指导实现。

**最小修正建议**：
- 邀请归因与健康数据授权分开；扫码不得自动授予教练读取历史记录或伤病信息的权限。
- 学员明确确认服务关系，并单独选择数据共享范围；伤病等医疗健康信息按敏感信息要求处理，落实必要性、单独同意与影响告知。
- 未获授权、已解绑或服务终止的教练，不得读取新的健康记录；历史记录/纠纷证据的保留范围另行约定。
- 明确运营访问审批、审计、导出权限、注销/删除流程、备份保留周期。
- 模型调用使用最小必要、去标识数据；明确模型供应商的处理角色、是否留存/用于训练、服务地点及可能的数据跨境义务；健康正文不得进入通用埋点。

**一手依据**：《个人信息保护法》第 6、15、21、23、28–30、55 条。不是所有传输都适用同一种告知同意模式，须区分委托处理与向其他处理者提供。

**验收**：越权访问、猜 ID、解绑后访问、导出越界、AI 日志泄露及撤回授权等负向用例全部通过。

### R03｜阻塞｜资质、责任与预算被误写成确定性结论

**证据**：[PRD:693–720](<docs/PRD.md#L693-L720>)；[成本清单:11–18](<docs/小程序上线成本与资质.md#L11-L18>)、[成本清单:124–140](<docs/小程序上线成本与资质.md#L124-L140>)。

- “不收款，因此只需要……”“不需要 EDI/ICP 许可证/等保”缺乏足够依据。线上信息/撮合服务及健康数据处理，并不会因不收钱自动消失。
- “代收再转款一概等于二清”混淆了自营销售、受托代收与第三方支付结算，不能不看业务关系就定性。
- “平台不是交易一方”描述合同角色，不是免责条款；投诉、数据保护及依法应承担的责任仍应确认。
- 微信类目、认证优惠、AI 登记与算法备案、等保适用性需分别核验，不能用一句免责声明替代。
- [成本清单:17](<docs/小程序上线成本与资质.md#L17>)仍把用户方案称为 C，[成本清单:96](<docs/小程序上线成本与资质.md#L96>)仍“推荐 V1 自营”，与已选 A 不一致。

**最小修正建议**：将法律/平台类条目改成“已核实 / 待确认 / 本版不启用的技术能力”。A 版确定不接支付功能，但许可义务按实际业务确认；用业务与数据流图向微信平台、当地主管部门或具备相关经验的法律专业人士核实。不得仅凭代办营销材料作结论。

**验收**：上线前有主体、业务类目、APP/域名备案区分、AI 服务义务、个人信息处理与投诉处置的逐项确认记录；外部受理时间不列为开发方保证。

### R04｜重要｜回填奖励会把“填得勤”误导为“数据可信”

**证据**：[PRD:173–183](<docs/PRD.md#L173-L183>)、[PRD:325–334](<docs/PRD.md#L325-L334>)、[PRD:641–655](<docs/PRD.md#L641-L655>)。

同一个教练既自报成交，又因回填得到曝光和“数据可信”标识。即使 100% 完成回填，记录仍可能不真实；“未回填算分母”只能改善完整率，无法证明成交。冷启动“按城市均值回填”也可能根本没有足够样本。

**最小修正建议**：
- 去掉对外“数据可信”徽章；回填完整率与实际成交转化率分别统计。
- 未成交、仍在沟通、未知都允许如实填写，不按“已成交”金额或数量奖励；不强迫用户提供金额。
- 分列“教练自报”“学员确认”“有服务活动证据”“未知”；只有确有证据的维度才可标注核验。
- 同步观察训练完成、实际反馈、关系留存和抽样访谈。回填不是“唯一价值证据”。
- 7 天可触发提醒或标记未知，不应把仍在沟通的咨询强制认定失败；后续结果允许修订并保留审计记录。
- 初期用提醒与结果面板改善回填，不把单方自报直接叠加进公开推荐排名；没有样本时显示暂无数据，而非编造城市基准。

**验收**：重复/修改留痕；成熟窗口、有效咨询分母和状态定义清晰；统计报表不得把自报金额称为已验证 GMV。

### R05｜重要｜A 版缺少“服务关系确认”这个交付开关

**证据**：[PRD:319–364](<docs/PRD.md#L319-L364>)、[PRD:438–455](<docs/PRD.md#L438-L455>)、[PRD:519–561](<docs/PRD.md#L519-L561>)。

ER 图出现 `COACH_STUDENT`，却没有对应字段、状态、发起/确认/终止规则。平台没有支付回调，自报“已成交”、提交咨询或扫邀请码都不能自动证明服务已开始、更不能自动授权。图上计划与训练依赖教练关系，文本又允许没有教练的自助训练；服务包改价后也缺历史约定快照。

**最小修正建议**：
- 咨询状态与服务关系拆开。服务关系采用待双方确认 → 生效 → 到期/解除；开始/结束时间、套餐说明及价格快照、数据共享范围、确认时间有明确记录。
- 训练和身体记录归属学员账户，授权关系控制访问，不归属某个教练；无教练用户也能记录。是否仅允许一个当前主教练需显式约定。
- 到期后停止新增访问，保留学员历史；新教练不自动获得旧教练私有备注或所有历史健康信息。
- 将“线下成交”统一为“平台外成交”，避免把线上指导误写成线下业务。
- [离线同步规则](<docs/PRD.md#L275-L278>)不能笼统以客户端为准。训练记录用唯一事件标识防重，编辑以版本检测冲突；计划发布版本与学员训练事实分开，不能被旧客户端覆盖。

**验收**：先咨询后成交、未成交、存量学员邀请、无教练自助、换教练、服务结束、教练封禁及重试/多端冲突均有可执行流程。

### R06｜重要｜教练可以通过解除关系压制差评

**证据**：[PRD:347–357](<docs/PRD.md#L347-L357>)。

文档一面允许服务结束后评价，一面禁止“已解除关系”的学员评价。教练终止关系即可阻断评价；而只等待 21 天又不能证明真实接受过服务。

**最小修正建议**：评价资格依据历史服务证据或双边确认，而非当前关系是否有效；结束/投诉/解绑不能自动剥夺历史评价权。咨询评价与服务评价分开，未核实付款不能展示“已购”标识。证据不足时可以先收集私密反馈，延后公开评分与排名。

**验收**：被解除关系的真实服务学员仍可在约定窗口评价和申诉；仅咨询者不能冒充已接受训练服务的学员。

### R07｜重要｜MVP 范围、上线周期与年度预算不匹配

**证据**：[PRD:121–154](<docs/PRD.md#L121-L154>)、[页面清单](<docs/PRD.md#L596-L633>)、[里程碑](<docs/PRD.md#L748-L762>)；[项目说明:14](<README.md#L14>)；[成本时间线](<docs/小程序上线成本与资质.md#L146-L159>)。

- 34 个页面中 33 个标为 P0，同时包含 AI 导购、对话、计划、排序、评价申诉、离线同步和多角色后台；没有人员确认、逐项估算或安全测试预算。
- 4–6 周上线、PRD W6–W7 提审上线、成本文档 W9 上线互相矛盾；成本时间线仍有 A 版不启用的支付接入。
- 3,000–8,000 元是未经用户量/模型用量校准的基础开销假设，不是完整上线报价。排除了人力并不意味着专业审查、合规准备、内容维护、客服与监控没有成本。

**最小修正建议**：首期保留“广场 → 主页 → 咨询 → 双方确认 → 计划/记录 → 教练反馈”的单一闭环；AI 先服务教练草稿。延后 AI 导购、复杂排名、公开评分、通用 AI 长对话、复杂离线多端合并。分别估算“可内测”“可提交审核”“批准公开发布”，外部审批不纳入固定保证日期。

**验收**：给每个 P0 标责任人、依赖、开发/测试工量和缺人降级方案；预算列出基础设施、按量 AI、人工服务/内容审核与合规准备，不再给无条件总价。

### R08｜重要｜“30 秒”把界面效率和专业判断混为一谈

**证据**：[PRD:103–115](<docs/PRD.md#L103-L115>)、[PRD:280–299](<docs/PRD.md#L280-L299>)。

“任何单个学员日常操作 ≤30 秒”和“P50 ≤30 秒”不是同一标准；也没有依据证明超过阈值教练就回微信。若套在计划审核、伤病判断上，会鼓励机械采纳 AI。

**最小修正建议**：只对低风险常规操作测量界面摩擦，例如打开记录、标记已读、保存草稿；专业审核不设秒级强制上限。按任务类型统计 P50/P90、总耗时及返工/质量，不以越快越安全为假设。

**验收**：区分操作时间与阅读/判断时间；风险升级与人工审核不受速度激励；与教练原工作流对照测试后再确定目标。

### R09｜重要｜“自主定价”被未确认的最低价规则限制

**证据**：[PRD:215–245](<docs/PRD.md#L215-L245>)。

用户确认的是教练自主定价，文档却加入 99 元/月下限、三档模板和低价人工审批。尚无证据证明这个金额代表质量；单次服务、月包和体验包的比较口径也不同。

**最小修正建议**：价格和服务方式由教练设置；平台统一“币种/周期/包含内容/响应说明”的展示格式，审核虚假宣传和缺失信息，而非未经用户确认地限定最低价格。建议价只作可选参考。

纯线上指导不需要默认锁城市；可以在一个教练社群招募，但城市过滤和线下服务应延后或另行确认。

### R10｜重要｜市场与论文证据被放大为错误或绝对结论

**证据**：[PRD:25–44](<docs/PRD.md#L25-L44>)、[PRD:115](<docs/PRD.md#L115>)、[海外调研:18](<docs/海外私教AI教练_事实清单.md#L18>)。

- 综述 14/24 项研究报告安全问题被写成“58% 输出/训练计划有缺陷”，分母被换掉。不能用它估算本产品危险率。
- “未查到跑通案例”被升级为“海外没有跑通案例”；订阅里包含 AI 也推不出“AI 不能收费”。
- 少量教练采访、某一平台的销售记录，不代表全国线上私教的付费区间或所有教练获客效率。

**最小修正建议**：改成“本轮检索未取得足够公开证据”；把竞品模式作为可选参考，AI 是否收费留待成本与付费意愿验证。来源缺失、二手转述、统计口径不匹配的数字不得成为硬验收标准。

**一手核验**：[原始综述](<https://pmc.ncbi.nlm.nih.gov/articles/PMC13343266/>)支持“研究报告了安全问题”，不支持“58% 全部计划出错”。研究之间人群、任务与模型不同，不宜进一步外推统一错误率。

### R11｜重要｜咨询通信与通知能力还没有实现定义

**证据**：[PRD:319–345](<docs/PRD.md#L319-L345>)、[PRD:135](<docs/PRD.md#L135>)、[数据模型](<docs/PRD.md#L519-L567>)。

“站内消息 + 微信客服组件”不能替代消息会话、教练路由与权限方案。当前没有会话成员、消息读取、禁止骚扰、封禁、未读和失败补偿模型；也没有证实提交咨询就满足微信客服可主动触达的条件。不能简单承诺所有人均能在 48h 内被主动发送消息。

**最小修正建议**：首版用按咨询单隔离的异步回复流；只有双方与授权客服能访问。订阅消息在用户授权且模板/场景支持时使用，不成功时站内可查。平台客服入口与教练会话明确区分，不把全部教练当作共享客服坐席。涉及联系方式展示与引导规则，须按当前类目及微信官方要求逐项核验，不声称所有微信号/二维码一概违法或必定被拒。

**验收**：教练 A 看不到 B 的会话；用户拒绝通知仍能完成服务；超出官方消息窗口时有明确降级，不能静默丢消息。

### R12｜重要｜试点指标尚不能证明“平台帮助教练获客”

**证据**：[PRD:639–655](<docs/PRD.md#L639-L655>)、[PRD:795](<docs/PRD.md#L795>)；[AI 配额](<docs/PRD.md#L263>)、[AI 成本目标](<docs/PRD.md#L427-L432>)。

- 教练把老学员搬入平台，只验证交付工具可用，不能算平台新增获客。应分开存量导入、广场新客、AI 自助转化三组。
- WDS 能衡量训练与回应，不自动证明学员处于已付费服务期；每周两练也未必适合所有训练频次。
- ≥50% 回填、4.6 评分、预约 100 单等都是待校准的试点阈值，不是已经验证的成功标准；切支付也不应仅由这两个数字触发。
- 每日 10 条免费问答相当于每月最多约 300 条，尚未给出输入/输出 token、历史长度和模型单价，无法确认 0.5 元/月上限。

**最小修正建议**：
- 分组报告：新客有效咨询 → 教练响应 → 双方确认开始 → 产生记录与反馈；存量学员独立报告工具留存与节省时间。
- 每个比率注明分母、去重粒度、观察窗、成熟队列与最小样本，未知成交单独列示。
- 由真实用量代入成本模型：调用数 ×（输入 token × 输入单价 + 输出 token × 输出单价）+ 重试、审核、存储等；先设日/月额度与费用熔断。
- 把所有阈值标为试点假设。是否接支付由双方需求、纠纷负担、合规准备与单位经济共同决定，不自动转 B。
- A 阶段尚未确认平台收费方式，不能把教练在平台外收费等同平台收入。工具订阅、获客服务费等都应另做付费意愿实验，不默认向任何一方收费。

## 九、边界修订（v1.4，用户否决了首版 AI 收紧建议）

首版建议「免费学员只用预审模板、不直接生成」。用户不同意，要求免费层有实际可用度，并提出**训练计划广场**：浏览现成计划、另存新建自己的计划、分享给别人、看热门。复核后接受该边界，理由与新增风险如下。

**为什么这个方案更合理**

- 免费层价值不依赖「AI 从零生成处方」，而是依赖**可复用的结构化计划**，安全面更可控。
- 用户从「被推荐」变成「自己挑选 + 自己调整」，符合「让学员自己选」的产品主张。
- 计划是结构化数据，可以块级校验、可审核、可统计完成率，比自由发帖社区便宜。

**新增的四个风险（已写入 PRD §5.3、§12.1）**

| 风险 | 对策 |
|---|---|
| UGC 计划包含不适合的动作或伤病建议 | 动作白名单校验 + 组次/频率合理性 + 风险词 + 新手默认只看官方/教练内容 + 举报 24h 下架 |
| 热门榜被刷 | 使用与完成去重、异常抽检、争议降权、官方/教练内容权重更高 |
| 抄袭与版权 | 改编标注、原作者署名、侵权投诉 72h、下架不影响已另存副本（页面说明） |
| 审核成本失控 | 只做结构化计划，不做图片/视频流；自动校验 + 抽检 + 举报驱动，不全量人工 |

**AI 边界（修订后）**：教练侧维持「必须人工确认」；免费侧做计划解读、记录分析、动作问答、**模板内调整建议（用户确认后生效）**，仍不提供从零个性化处方。这一条仍需用户最终确认。

**教练端**：用户明确无异议，维持 v1.3 设计（AI 副驾、工作台、交付、回填、服务包）。

## 十、四项取舍已确认（v1.5 冻结）

| 项 | 结论 | 落点 |
|---|---|---|
| 免费 AI 边界 | 保持「不给从零个性化处方」，免费层价值靠计划广场与解读/分析 | PRD §5.4.2、§3.2 |
| 计划广场可见性 | 未登录可浏览列表与详情；另存/收藏/开始训练需登录 | PRD §5.3.2、§8.2 |
| 学员分享审核 | 发布前 100% 自动校验 + 人工抽检 10–20% + 举报驱动；不做全量人工 | PRD §5.3.7 |
| 首期人群 | 增肌 / 减脂，18–28 岁；同步写入 18 岁年龄门槛 | PRD §1.2、§2.1、§5.5、§9.2、§11 |

**风险提示（已写入 PRD）**：18–28 岁人群偏年轻，增肌减脂内容容易滋生「速成」「焦虑营销」，文案审核需重点拦截；年龄门槛只做 18+ 断言，不做 28+ 限制。

## 十一、饮食计划的设计判断（v1.6 新增）

用户要求「教练可发布训练计划、饮食计划到广场」。饮食比训练更接近医疗，因此设计上做了分级，而不是把饮食当普通内容放开。

**核心判断：只做非医疗、非个性化的饮食内容**

| 级别 | 内容 | V1 | 理由 |
|---|---|---|---|
| L1 饮食原则 | 增肌减脂怎么吃、外食选择、蛋白来源 | 开放 | 科普性质，无个体风险 |
| L2 档位餐单 | 按体重档位给热量/蛋白区间 + 三餐示例 | 开放（官方/教练） | 用户自选档位，平台不为其开处方 |
| L3 个性化方案 | 结合疾病、过敏、孕产、用药的个体化饮食 | 不做 | 已进入临床营养/医疗边界，平台无资质审核 |

**为什么学员不能发布饮食计划**：训练计划做错多是无效，饮食计划做错可能过敏或伤身；UGC 饮食风险不可控，V1 只开放「另存/查看/分享」，不开放发布。

**硬性拦截**：日均 <1000 kcal、蛋白 >3g/kg、断食/极简/生酮减重/脱水/清肠/代餐替代正餐等词与方法直接阻断；疾病、孕产、未成年、术后、进食障碍相关词阻断并提示转介。

**待用户确认的三点**

1. 是否允许教练发布「按体重档位」的餐单？这是 L2 的边界，我按允许设计（用户自选档位，非平台开处方）。
2. 学员是否完全不能发布饮食计划？（现设计：不能发布，但可另存和分享）
3. 是否需要「按计划吃了几天」的打卡？现设计 P1，V1 只做查看与另存。

## 十二、学员发布饮食计划、饮食打卡、AI 发布助手（v1.7）

用户三项决定：允许档位餐单；学员可发布饮食计划（与教练分类展示、教练打标签）；要饮食打卡；发布表单由 AI 辅助配置。

**怎么落地**

| 决定 | 设计 |
|---|---|
| 档位餐单允许 | L2 开放给官方/教练/学员；用户自选档位，平台不为个人开处方 |
| 学员可发布饮食计划 | 同一套校验与禁止清单；列表/详情/分享页显示「学员分享 · 非专业建议」；教练内容显示「教练发布 · 已认证」；支持来源筛选 |
| 分类展示与教练标签 | 标签来自账号认证状态，不能自行修改或隐藏；热门排序中教练内容权重高于学员 |
| 饮食打卡 | 每日按餐次自评（早/午/晚/加餐），记连续天数与 7 日依从率；不做健康评分、不做体重归因 |
| AI 发布助手 | 自然语言 → 结构化草稿 → 发布者逐项确认 → 同一套校验 → 提交；AI 不直接发布 |

**新增风险与对策**

- 学员发布饮食计划误导他人：首次发布人工审核、标签强制、不进新手推荐、举报下架。
- 打卡造假用于刷热门：打卡不计入热门权重，只用于依从率与个人记录。
- AI 预填把热量/份量估错：字段标「AI 估算」、必须确认、可回溯预填版本。

**仍建议后续确认**

1. 学员首次发布是否都走人工审核？现设计仅饮食首次人工，训练保持自动 + 抽检。
2. 打卡是否给连续天数激励（如徽章）？现设计只在个人页展示，避免制造焦虑。

## 十三、异常饮食识别与架构（v1.8）

**新增功能**：AI 预填之外，把「筛出异常饮食」做成教练的日常待办，而不是让教练逐条翻打卡。

| 项 | 设计 |
|---|---|
| 触发 | 发布/另存饮食计划、每日打卡、教练查看学员详情（聚合近 7 天） |
| 判断 | 规则优先（热量、蛋白、餐次结构、过敏原、极端方法词），模型只做二次标记 |
| 输出 | 提示 / 需复核 / 阻断 + 原因 + 规则版本 |
| 去向 | 教练工作台「需关注」+ 运营复核队列；处理留痕 |
| 边界 | 不诊断进食障碍、不给学员贴「异常」标签、不自动发警告；可反馈误报调阈值 |

**为什么规则优先**：热量与蛋白阈值、过敏原冲突是确定性的，规则可解释、可审计；模型只处理「描述性信号」，避免把概率判断当结论。

**架构文档**：[系统架构与技术选型.md](<docs/系统架构与技术选型.md>) 已给出模块化单体 + AI 网关 + 规则引擎 + 审核队列的方案，待拍板三项选型（云厂商 / 后端语言 / 小程序框架）。

## 十四、技术选型拍板（架构 v1.1）

用户三项决定：腾讯云（已有服务器）、后端 Go（可读性优先）、跨端优先（为未来 App 减少改动）。

**跨端推荐：uni-app（Vue3 + TypeScript）**

| 方案 | 小程序 | App | 复用 | 判断 |
|---|---|---|---|---|
| uni-app | 编译 | 云打包原生 App | 70–85% | 推荐 |
| Taro + RN | 编译 | RN 目标 | 60–75% | 备选 |
| 原生 + RN/Flutter | 原生 | RN/Flutter | 低 | 违背跨端优先 |

**代价已写进文档，不粉饰**：App 阶段仍要单独做推送、登录、支付（iOS 可能要求 IAP）、商店合规、深链、强制更新，预计追加 4–8 周；uni-app 重页面性能不如原生，必要时局部换原生插件。

**架构相应变化**：后端由 NestJS 改为 Go（Gin + GORM + golang-migrate + asynq）；后台由 React 改为 Vue3 + Element Plus（与 uni-app 同语言）；前端分 `api/domain/platform/ui` 四层，页面不直接调用 `uni.*`，为 App 换壳保留边界。

**仍待确认**：uni-app vs Taro 的最终选择；AI 主备供应商（千问/混元）的优先级。

| 云厂商 | 腾讯云（复用现有服务器，DB/Redis 走云服务） |
| 后端 | Go（Gin + GORM + golang-migrate + asynq） |
| 跨端框架 | uni-app（Vue3 + TS + Vite），一套代码出小程序/H5/App |
| AI 主模型 | MiMo-V2.6 Flash（用户指定，价格优先） |
| AI 降级 | 混元 lite / 千问 Flash，网关自动切换 |
| 兜底 | 规则 + 模板，模型不可用时不阻塞业务 |

**MiMo 接入前必须核对（已写入架构文档 §13）**：官方 API 的准确 SKU 名称、计价与免费额度、生成式 AI 备案状态、JSON/结构化输出支持、限流与 SLA、数据条款与开票。

**判断**：选低价模型对 MVP 合理，但训练计划与饮食结构化对输出稳定性要求高，建议上线前用 200–300 条真实输入做一次成功率与修复率对比；若 Flash 档结构合法率明显低于 Pro，计划生成可单独升档，其余保持低价档。

**跨端遗留风险**：uni-app 重页面性能与 App 商店合规仍需在 Phase 2 单独投入，预计追加 4–8 周，不要按「一套代码零成本上架」做预算。

**关键设计落点**

1. 三个事实分离：`appointment` / `deal_status` / `service_relation` 独立建模。
2. 模板与实例分离：`plan_template` → `plan`，另存后脱钩；发布后编辑走 `plan_version`。
3. 数据归属与授权：记录归学员；`data_grant` 按范围授权，解绑即失效。
4. AI 可追溯：`ai_run` 记录模型、prompt 版本、token、成本、安全状态。
5. 异常与审核：`anomaly_flag`、`moderation_task`、`audit_log` 全留痕。
6. 金额最小化：成交只存自报区间，不存精确金额，避免被误当交易事实。

**本版未覆盖**：教练发布计划给学员、点评/周报发送、打卡提交、收藏与分享链接、邀请码、AI 模板内调整、订阅消息授权、后台申诉处理。已在 `api/README.md` 列出，作为下一批。

**验证**：OpenAPI 通过 YAML 解析与 `$ref`/路径参数检查（69 路径、83 操作全部可解析）；ER 与契约的对应关系见 ER 文档 §9。
