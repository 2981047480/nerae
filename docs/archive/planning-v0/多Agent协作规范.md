# 多 Agent 协作规范

目标：让多个子 Agent 在**不互相覆盖、不重复返工、不需要 Lead 逐行盯**的前提下并行开发，产出可合并、可验收、可回滚的成果。这是「cursor multi-agent」效果在本仓库的落地方式：不是让 Agent 更自由，而是让边界更清楚。

适用范围：任何在本仓库执行开发任务的 AI Agent 与人类协作者。任务源是 [backlog/tasks.yaml](<../backlog/tasks.yaml>)，本规范解释怎么用它。

## 1. 角色

| 角色 | 职责 | 不做 |
|---|---|---|
| **Lead（集成者）** | 拆波次、定契约、分配任务、验收、解决冲突、维护文档索引 | 不并行写多个模块的业务代码 |
| **Contract Steward（契约持有人）** | 独占 `api/openapi.yaml`、`api/tests/`、ER 对应章节；串行修改并跑回归 | 不在业务任务里顺手改契约 |
| **Worker（执行者）** | 一个任务、一个作用域、完整交付（代码+测试+证据） | 不跨作用域修改、不重构无关代码 |
| **Reviewer（轮值）** | 复核另一个 Worker 的交付：契约一致性、越权、测试有效性 | 不复核自己的任务 |
| **QA / Ops** | 质量门、部署、指标、种子内容 | 不以"测试通过"替代真实运行验证 |

同一波次内，Worker 数量不超过任务板 `max_parallel`；Reviewer 从已完成任务的 Worker 中轮值，不额外占并行额度。

## 2. 任务卡：唯一的任务单位

一张卡 = 一个可独立验收的交付，**≤3 人日**。超过就拆，不能靠"我尽量做完"。

**Definition of Ready（可开工）**

1. `depends_on` 全部 `done`。
2. `scopes` 与同波次其他任务不重叠，共享文件已有所有者。
3. 需要的契约、设计 tokens、页面模板、数据表结构已存在。
4. 验收标准可执行（有命令、有预期结果），不是"界面好看"这类主观描述。
5. 任务没有同时包含"改契约"和"写实现"两件事。

**Definition of Done（可收工）**

1. 只改了 `scopes` 内文件；无临时调试代码、无注释掉的死代码。
2. 自检命令通过：lint、类型检查、单元/契约测试、构建。
3. 新增行为有测试；修复缺陷有复现用例。
4. 契约有变更时，已重新生成客户端/服务端产物并提交。
5. 交付说明含：改动文件、验证命令与结果、未完成项、影响面。
6. Reviewer 通过，Lead 复跑验收命令通过。

## 3. 波次并行模型

```
W0  契约收口（串行链） + Git 基线 + 文档决策（并行）
W1  骨架：Go / tokens / CI
W2  基础设施 / 小程序骨架 / 后台骨架
W3  身份与档案
W4  教练与服务包 / 双广场
W5  关系 / 交付 / 个人计划（首个闭环）
W6  记录 / 免费发布 / AI 网关
W7  饮食 / 异常
W8  审核 / 后台
W9  质量门
W10 试点准备
```

三条硬规则：

1. **跨波次才能并行**：并行任务之间的依赖必须指向更早波次。
2. **同波次只有 `tail` 能依赖同波次任务**：`tail` 负责路由接线与冒烟，等并行任务全部完成再跑。
3. **同一文件同波次只有一个写者**：共享文件见 §4。

为什么这样切：并行度来自"不同目录、不同契约面"，不是"多人同时改一个文件"。同文件并行是最贵的协作方式，冲突成本高于并行收益。

## 4. 写作用域与共享文件

- 每个任务声明 `scopes`（路径前缀）。写之前确认目标路径在范围内。
- 两个任务的 scope 互为前缀（如 `apps/api/internal/modules/auth/` 与 `apps/api/internal/modules/auth/login/`）视为重叠。
- 生成物（`packages/api-types/`、`packages/design-tokens/` 的产物）只由生成命令更新，不手工编辑；提交时附生成命令。
- 共享文件未指派所有者时，任何 Agent 不得修改：

| 共享文件 | 所有者 |
|---|---|
| `api/openapi.yaml`、`api/tests/` | Contract Steward（W0 串行） |
| `apps/api/internal/server/routes.go`、`modules.go` | 该波 `INT-*` / `DIET-02` |
| `apps/api/migrations/` | SETUP-05；后续新增迁移单列任务 |
| `apps/api/go.mod`、`package.json`、`pubspec` 类依赖清单 | 该波第一个需要新增依赖的任务，或 Lead |
| `README.md`、`AGENTS.md`、`docs/开发计划-v1.0.md` | Lead |
| `packages/design-tokens/tokens.json` | 设计系统任务；变更需 Lead + 设计确认 |

需要新增依赖时：在任务交付说明里列出"新增依赖 + 理由 + 许可证"，由 Lead 批准后写入，避免多个 Agent 并发改依赖清单。

## 5. 契约先行

顺序固定：**改契约 → 生成产物 → 跑契约回归 → 写实现 → 集成测试**。

- 契约变更必须由 Contract Steward 执行，且是独立任务（不混在业务任务里）。
- 破坏性变更（删除字段、改类型、改语义）必须由 Lead 批准，并在 `docs/adr/` 记录原因与迁移方式。
- 实现与契约不一致时：以契约为准，或先改契约再改实现；不允许"代码这样也能跑"。
- 契约回归（`api/tests/`）是硬门：失败不能合并；不允许通过放宽断言、加 skip、改期望值变绿。

## 6. Git 与合并（SETUP-01 之后）

- 主分支 `main` 始终可构建；任务在 `task/<id>-<slug>` 分支开发。
- 一个小步一次提交；提交信息用 Conventional Commits（`feat:`、`fix:`、`test:`、`docs:`、`chore:`），正文写"为什么"。
- PR 描述直接使用任务卡的 `deliverables` 与 `acceptance`；PR 标题含任务 ID。
- 合并顺序：先合契约/迁移/生成物，再合依赖它们的实现；同一波次的 `tail` 任务最后合。
- 禁止 force-push 到 `main`；禁止把 `.review/`、`.pnpm-store/`、虚拟环境、密钥提交进仓库。
- 合并前必须 rebase 到最新 `main` 并重跑自检；冲突由后合者解决，解决后通知先合者。

## 7. 领取与占用

1. 在任务板把 `status` 改为 `claimed`，记录领取者与时间。
2. 开工改 `in_progress`；超过 1 个工作日没有进展，Lead 有权收回。
3. 同一任务只能有一个所有者；需要协作时拆成子任务，而不是两人改同一批文件。
4. 任务阻塞时改 `blocked`，写清：阻塞原因、已尝试方案、需要谁做什么决定、预计解除条件。**不要静默停摆。**

## 8. 交付、复核与验收

三道关，缺一不可：

| 关卡 | 谁 | 检查什么 | 失败处理 |
|---|---|---|---|
| 自检 | Worker | lint/类型/测试/构建，作用域合规 | 自行修复，不提交 review |
| 同行复核 | 另一 Worker | 契约一致性、越权与敏感数据、测试是否真实验证、边界条件 | 退回 `in_progress`，写明问题 |
| Lead 验收 | Lead | 复跑命令、读 diff、确认无跨作用域修改、更新任务板与文档 | 不通过则退回，不允许"先合并再说" |

复核清单（默认必查）：

- 是否有未授权数据被读取、返回或写日志？
- 是否有客户端可伪造的信任字段（来源标签、认证、证据等级）？
- 版本冲突、幂等重放、并发撤权是否有处理？
- 失败路径是否返回统一错误码，而不是 500 或静默成功？
- 新增测试是否会在旧实现上失败（否则是假测试）？
- 文档/契约/生成物是否同步？

## 9. 冲突处理

| 冲突类型 | 处理 |
|---|---|
| 文件被他人修改（`FS_STALE_VERSION`） | 重新读取，基于新内容重做本轮改动；不覆盖他人修改 |
| 必须修改别人作用域 | 停止，上报 Lead；由 Lead 调任务或合并任务，不自行越界 |
| 契约与实现冲突 | 以契约为准；确需变更先走契约任务 |
| 两个任务都需要同一共享文件 | 由共享文件所有者统一改，或拆出独立任务排到该波 `tail` |
| 设计 tokens 与页面实现冲突 | 以 tokens 为准；页面需要新 token 时提给设计任务，不在页面里写魔法值 |
| 依赖版本冲突 | Lead 决定统一版本；不允许各任务各自锁定不同大版本 |

## 10. 质量门

**每波结束**（Lead 执行，全绿才进下一波）：

```sh
python3 backlog/validate.py
npx --yes @redocly/cli@1.34.3 lint api/openapi.yaml
PYTHONDONTWRITEBYTECODE=1 api/tests/.venv-py311/bin/python \
  -m unittest discover -s api/tests -p 'test_*.py'
# 应用脚手架建立后追加：
# make lint && make test && make build
```

**每个里程碑**（M1–M6）额外要求：

- 可演示：按验收脚本走通，不靠口述。
- 可回滚：数据库迁移有 down 或补偿脚本；部署有上一版本镜像。
- 有证据：命令输出、截图、测试报告存入 `docs/qa/` 或 `.review/`（不入库）。

## 11. 上下文与知识管理

- **事实只有一个来源**：产品范围看 PRD，数据看 ER，接口看 OpenAPI，视觉看设计系统，规范看工程规范。不要在每个 Agent 的 prompt 里复制一份，容易漂移。
- 术语以 [CONTEXT.md](<../CONTEXT.md>) 为准；新概念先加词条再用。
- 重要取舍写 ADR（`docs/adr/`）：难以逆转、有真实替代方案、未来读者会问"为什么"。
- 每个应用的 README 写：怎么跑、怎么测、目录结构、已知限制。
- 长文档开头给"读这一节能回答什么"，避免 Agent 全文漫游。
- 决策变更要改文档，不只改代码；文档与代码不一致时，以文档为讨论基础、以契约为实现边界。

## 12. 反模式（出现即停）

1. 一个任务改 20 个文件、跨 3 个模块。
2. 两个 Agent 同时改 `routes.go`、`package.json`、`tokens.json`。
3. 在业务任务里"顺手"改契约或 ER。
4. 测试通过靠删断言、加 skip、放宽正则。
5. 先写实现，再补契约（顺序反了）。
6. 用"应该可以""大概没问题"作为验收结论。
7. 把 `.review/`、构建缓存、虚拟环境提交进仓库。
8. 未确认产品取舍就实现（尤其 R06 联系路径、R03 日程规则、评价是否公开）。
9. 在日志、错误信息、AI prompt 里带健康正文。
10. 任务卡不写验收标准就开工。

## 13. 运行指标（Lead 每周看）

| 指标 | 目标 | 说明 |
|---|---|---|
| 并行度 | 每波实际并行任务数 / 计划数 ≥0.8 | 太低说明依赖切分有问题 |
| 返工率 | 复核退回任务 / 总任务 ≤15% | 高则任务卡不够具体或契约不清 |
| 阻塞时长 | `blocked` 平均 ≤0.5 天 | 长说明决策缺位 |
| 复核时长 | ≤0.5 天 | 长说明 Reviewer 不足或任务太大 |
| 契约回归 | 100% 通过 | 任何失败都阻断合并 |
| 跨作用域修改 | 0 | 出现即流程失效 |

## 14. 委派模板（Lead → 子 Agent）

```md
你是 <角色>，只做任务 <ID> <标题>。仓库根目录：<path>。

必读（按序）：AGENTS.md、backlog/README.md、任务卡、相关契约/文档章节。
写作用域：<scopes>。除此之外不要改任何文件；需要改时停下报告。
依赖状态：<depends_on 已完成情况>。
交付物：<deliverables>。
验收命令：<命令与预期>。
约束：<本任务特有的硬约束，例如不得改契约、不得新增依赖>。

完成后：跑验收命令 → 写交付说明（改动/验证/风险/影响）→ 任务板改 review。
不要声称完成如果命令没跑过；不要把"能构建"当成"功能正确"。
```

子 Agent 的回报必须包含：任务 ID、改动文件、验证命令与输出摘要、未完成项。缺一项视为未交付。
