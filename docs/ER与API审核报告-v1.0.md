# ER 与 OpenAPI 审核报告

> 日期：2026-10-22。范围：刚交付的数据模型与 API 契约，不是后端实现审计。
> 方法：Lead 工具校验与交叉验证，加两个只读子代理，分别检查 Standards（规范）和 Spec（需求）。两轴保留独立结论，不合并排名。
> 原稿未修改，未搭建 Go 工程。验证工具缓存和生成冒烟产物仅保存在工作区临时目录。

## 结论

**暂不建议将当前契约冻结后直接据此实现核心业务。** 结构方向可保留，但正式 OpenAPI 校验有错误，且服务关系发起、教练交付、饮食编辑和 AI 人工确认存在实质缺口。

上一轮“YAML 能解析、引用完整，因此可以直接开工”和“未覆盖部分不影响核心闭环”的判断过早。本轮予以修正：类型能生成不等于业务闭环成立。

以下均为设计/契约问题，**不是已经验证的线上漏洞、数据泄露或模型误诊**。未实现服务，无法用真实 HTTP、数据库或并发请求验证运行时行为。

### T1｜确定错误：参数默认值层级不符合 OpenAPI 3.0

[OpenAPI:520–526](<api/openapi.yaml#L520-L526>) 把 `default: recommended` 写在 Parameter Object，应该写进该参数的 `schema`。正式校验报：`Property default is not expected here`。

**修正**：移动至 `schema.default`，再跑正式校验，不靠忽略规则消除错误。

145 个警告具体为：83 个缺 `operationId`、59 个操作未描述 4xx、2 个占位服务域名、1 个缺许可证字段。占位域名本已注明是示例，不等同产品缺陷；警告也不是 145 个业务阻塞。但稳定 `operationId` 和实际错误响应对 Go/TS 契约协作需要补齐或明确处理。

### T2｜工具链差异：价格枚举在两种解析链中含义不同

同一 [价格枚举](<api/openapi.yaml#L520-L522>) 写为 `299_499`、`499_799`（未加引号）：
- 当前 Python/PyYAML 实际解析为整数 `299499`、`499799`。
- [TS 冒烟产物:987](<.review/contract-audit-20261022/api-types-smoke.d.ts#L987>) 保留为字符串 `"299_499"`、`"499_799"`。

这不是声称正式 lint 已报告第二个错误，而是实测的跨工具解释差异。**修正：字符串枚举全部显式加引号，统一 YAML 解析规范，避免校验/生成链各自理解不同。**

## Standards｜规范审查

以下保留规范子代理的 5 项结论及其顺序。P1 为高影响契约/模型问题，P2 为明确的接口衔接或边界问题。

### S1｜P1：撤回授权缺少并发保护

**证据**：[授权 PUT:1165–1187](<api/openapi.yaml#L1165-L1187>)、[授权版本:2018–2027](<api/openapi.yaml#L2018-L2027>)、[ER 授权原则:10](<docs/数据模型与ER设计.md#L10>)。

响应已有 `version`，请求没有 `expectedVersion` 或 `If-Match`，且 `revoked` 默认 false。反例：设备 B 已撤回，设备 A 的旧保存/重试随后到达，契约无法区分过期写与用户主动重新授权。

**最小修正**：原子比较版本；冲突返回 409/412；结束关系后不能恢复授权；后台任务实际读取敏感数据时也重查有效授权。当前没有实现，不能断言已发生越权。

### S2｜P1：训练模板正文与历史版本缺少明确落库位置

**证据**：[ER 模板与实例:146–191](<docs/数据模型与ER设计.md#L146-L191>)、[不可变发布原则:12](<docs/数据模型与ER设计.md#L12>)。

`plan_template` 没有训练正文或版本引用，`plan_day` 和 `plan_version` 只属于个人 `plan_id`。发布一套公开训练模板后，其训练正文及修订历史没有明确对应实体。

**最小修正**：补模板版本实体或等价的版本化正文设计；公开详情、另存来源、审核与下架都绑定具体版本。模板下架与已有私人副本的后续安全提示也应区分，不默认删除用户历史记录。

### S3｜P1：后台认证主体未闭合

**证据**：[后台登录模型:2110–2121](<api/openapi.yaml#L2110-L2121>)、[ER 身份表:76–99](<docs/数据模型与ER设计.md#L76-L99>)、[审计主体:232](<docs/数据模型与ER设计.md#L232>)。

契约用 username/password 登录，模型只有微信身份和角色，没有管理员用户名、密码哈希或外部 IdP 映射，无法据此定义凭据来源和审计主体。

**最小修正**：明确独立管理身份/凭据映射或外部 IdP，审计绑定不可变主体 ID；不能用普通客户端传入的 role 授予管理权限。

### S4｜P2：训练日输入与输出不闭合

**证据**：[开始训练:936–942](<api/openapi.yaml#L936-L942>)、[TrainingDay:1895–1913](<api/openapi.yaml#L1895-L1913>)、[ER plan_day:189](<docs/数据模型与ER设计.md#L189>)。

开始训练接收 `planDayId`，计划详情中的训练日却不返回该 ID。用户点第二个训练日时，没有契约字段能直接把该日关联到会话。

**最小修正**：返回只读日 ID 与所属计划版本，或改用明确的 `(planId, version, weekIndex, dayIndex)` 键。

### S5｜P2：离线去重键可能跨账号冲突

**证据**：[clientEventId:942](<api/openapi.yaml#L942>)、[全局唯一约束:209](<docs/数据模型与ER设计.md#L209>)。

契约没有限定键的生成域。两个账号都提交 `"1"` 符合当前字段定义，却触发全局唯一键冲突。

**最小修正**：使用 `(user_id, client_event_id)` 唯一键；定义同键同内容重放、同键异内容冲突、保存期限与并发行为。不要把“写了幂等头”当作已经定义了完整幂等协议。

**本轴小结：5 项；最紧要的是授权撤回并发保护，其次是模板版本与后台认证模型。**

## Spec｜需求符合性审查

以下保留需求子代理的 6 项结论及其顺序；与规范轴重合的训练日问题保留在两轴中，不将两轴数量相加作为独立缺陷总数。

### Q1｜阻断首批：没有发起服务关系的接口

**证据**：[PRD:597–608](<docs/PRD.md#L597-L608>)、[ER 发起状态:271–273](<docs/数据模型与ER设计.md#L271-L273>)、[API 关系列表/确认:1109–1133](<api/openapi.yaml#L1109-L1133>)、[教练确认:420–431](<api/openapi.yaml#L420-L431>)。

两方确认均要求已有 ID，但没有创建关系、取得该 ID、设置服务期与套餐快照的契约。新学员预约后无法进入真实服务。

**最小修正**：补独立发起流程及双方身份、服务期、套餐版本快照；明确教练发起是否同时算教练确认。不允许默认把“已成交自报”或预约状态当作关系已生效。

### Q2｜明确延期，但仍阻断首批：缺少教练计划交付与点评

**证据**：[已披露未覆盖项:55–64](<api/README.md#L55-L64>)、[PRD 首批范围:158–168](<docs/PRD.md#L158-L168>)、[交付指标:940](<docs/PRD.md#L940>)。

这些缺项已坦承，不是隐瞒；但它们本身就是首批闭环，不能因此声称“不影响核心闭环”。即便手工创建关系，教练仍不能完成计划发布与反馈。

**最小修正**：首批至少补“生成/编辑草稿 → 教练确认发布 → 学员读取 → 训练记录 → 教练点评”；周报自动化、海报等才可另排后续。

### Q3｜首批语义缺口：按计划开始训练无法关联具体日

**证据**：[PRD:529–540](<docs/PRD.md#L529-L540>)、[TrainingDay:1895–1913](<api/openapi.yaml#L1895-L1913>)、[会话创建:936–942](<api/openapi.yaml#L936-L942>)。

需求是点选计划里的训练日开始，而返回模型缺日 ID。该项同时违反规范衔接（S4）和用户流程。

**最小修正**：补稳定训练日标识与计划版本，并测试“另存模板 → 选第 2 天 → 开始训练 → 记录关联正确”。

### Q4｜P0-B：饮食计划另存后没有修改份量的接口

**证据**：[PRD:348–351](<docs/PRD.md#L348-L351>)、[饮食另存/读取:751–795](<api/openapi.yaml#L751-L795>)、[通用编辑:709–722](<api/openapi.yaml#L709-L722>)。

“米饭 100g 改成 150g”没有定义的写入口；通用 PATCH 只接收训练 days。饮食个人实例的读取还复用了公开模板响应，混淆模板与个人副本。

**最小修正**：定义饮食实例的餐次/食材/份量 schema、编辑接口、版本与独立快照；训练和饮食采用明确的联合类型，不能都塞进任意 JSON。

### Q5｜P0-B：AI 预填的人工确认无法在契约中证明

**证据**：[PRD:432–444](<docs/PRD.md#L432-L444>)、[预填响应:2055–2064](<api/openapi.yaml#L2055-L2064>)、[发布请求:861–868](<api/openapi.yaml#L861-L868>)。

预填结果没有运行/草稿版本标识，发布只接收任意 `draft`；“原样转交 AI 结果”和“确认过字段后提交”无法从协议区分，误填也难回溯。

**最小修正**：绑定 `aiRunId`、草稿/内容版本、需要确认的估算字段和发布确认记录；服务端以匹配版本校验。发布者确认只证明确认动作，不能充当专业营养审查或数值准确性保证。

### Q6｜P0-B：异常饮食识别缺少实际摄入证据

**证据**：[PRD:459–478](<docs/PRD.md#L459-L478>)、[打卡 schema:1967–1981](<api/openapi.yaml#L1967-L1981>)、[ER 打卡:216](<docs/数据模型与ER设计.md#L216>)、[个人档案:1766–1780](<api/openapi.yaml#L1766-L1780>)。

目前只有四餐 boolean、自评分和可空备注，没有实食/份量、个人过敏原。连续三天全打勾既可能吃足，也可能只吃少量或换成过敏食物；输入相同，不能推出真实低摄入或个人过敏冲突。

**最小修正**：没有观察证据就输出 `insufficient_data`，仅提示已观察事实，不能用计划档位推断实际摄入。若保留摄入识别，补自愿提供、可修正、带来源与确认记录的实食信息/过敏原，并按健康数据授权读取。本审核不背书现有固定热量或蛋白阈值。

**本轴小结：6 项；最严重的是服务关系没有发起入口，以及首批交付/点评闭环缺失。**

## Lead 补充核验与落地约束

以下是主审发现的补充约束，不混入两位独立子代理的统计，也不虚构为已发生的运行时故障：

- **核心请求 schema 仍过松。** [ServicePackage](<api/openapi.yaml#L1795-L1808>)、[DietCheckin](<api/openapi.yaml#L1967-L1981>)、[BodyMetric](<api/openapi.yaml#L1959-L1966>)和[AuditAction](<api/openapi.yaml#L2122-L2126>)没有 required 字段；按 schema，空对象并未被排除。[发布请求](<api/openapi.yaml#L861-L868>)甚至不要求 draft 存在。需区分 Create/Update/Read 模型，补必填、范围、readOnly/writeOnly 与互斥内容类型；缺失字段应返回明确 422，不能靠前端自行猜。
- **伤病信息不回显只写在说明里。** [StudentProfile](<api/openapi.yaml#L1766-L1780>)被 GET/PUT 共用，`injuryNotes` 未设 writeOnly，生成类型仍包含该字段。应拆读写 schema，并明确 `privacyLevel=public` 不能覆盖敏感字段的按关系授权。这里不是断言服务已经泄露数据，而是契约没有固化约束。
- **站内咨询消息尚未建模。** [PRD:610–615](<docs/PRD.md#L610-L615>)要求咨询单隔离会话，现有 [通知读取/标记已读](<api/openapi.yaml#L1356-L1384>)不等于聊天发送与会话授权；应补最小异步回复流，或明确一期采用何种可用且获授权的联系路径。
- **ER 仍是模型草案，而非完整可迁移 DDL。** 31 张表中相当一部分只是字段列表；发布模板、饮食个人实例、私有文件授权、后台凭据、幂等记录等仍待补齐，不能从“31 表”数量推出可直接建库。

## 修正后再验收的条件

1. 正式 lint 无结构错误；警告逐项修正或有明确接受理由；字符串枚举跨工具一致。
2. TS 类型生成通过；在有 Go 的环境运行固定版本 oapi-codegen 并编译；不再仅提供未验证的生成命令。
3. 用同一组虚构用户演练两条闭环：
   - 预约 → 联系 → 发起关系 → 双方确认 → 授权 → 教练发布 → 学员记录 → 教练反馈。
   - 公开训练/饮食模板 → 另存 → 编辑 → AI 预填确认 → 发布审核 → 浏览/分享 → 打卡。
4. 用负向场景验收撤权、旧版本重放、跨教练访问、重复写与下架私密内容访问；预期响应写进契约与测试用例。
5. 异常识别区分“计划风险”“实食记录风险”“信息不足”，阈值由适当专业审查确定并版本化；不以类型校验、用户确认或免责声明证明健康安全。

**汇总：独立 Standards 5 项，最严重为撤权并发；独立 Spec 6 项，最严重为关系发起和首批交付断链。两轴结论均需要修订后复核。**
