# Nerae 用户任务与状态流程

版本 1.1 · 2026-10-27；F01 按用户要求改为训练后默认记录与逐组完成后记录。当前是开发输入；旧 UI 参考已撤销和删除，设计逻辑见 `docs/design/DESIGN_FOUNDATION.md`，当前没有可用业务服务。业务范围以 PRD 为准，字段以 OpenAPI v1.2.0 为准。

## F01 学员记下实际训练

**结果**：实际做过的动作与组成为一份可修改、可恢复的记录。用户决定实际重量、次数、日期和是否采用计划；App 负责组织、减少重复输入、保存、恢复和校验；AI 不推测完成事实。

1. 首页主操作是「记录训练」或「继续填写」。计划详情可「用这份计划记录」，不进入训练播放器。不按计划练时可添加实际动作与组；休息日也允许补记，不替用户重排未来安排。
2. 必要时登录并确认 18+，取消回到原计划/训练日。完整健康档案不是浏览或普通记录的前置条件。模板另存/更换未来安排仍须明确确认，已有记录不受覆盖。
3. 默认「训练后记录」：按动作展开各组，填写实际值后点「保存记录」。上次数据只作参考，明确沿用才填写；空白组不算完成，半行输入要补齐或移除。
4. 可切换「每组完成后记录」：选择动作，练完一组填值并点「记下」。可任选动作，不自动跳组、休息、倒计时或开始/暂停训练。两个模式使用同一记录与稳定组 ID。
5. App 暂存未提交输入、模式和当前动作；退出、返回、刷新后继续填写。最终保存汇总已确认及本次有效填写的组；重复保存更新原记录，不能创建另一份副本。
6. 日期是训练发生日；录入时间仅作保存与审计，不能显示成推测的组完成时刻。手填时长动作只代表实际秒数，不启动时钟。
7. 保存后说明保存位置、实际组数和结果，留在同一记录可修改；返回首页不会重建草稿。本地样机不宣称云同步，正式离线版按下表验收。

已确认的实际组跨端恢复时，动作条目保持用户排列，条目内的组按组序号排列；同一动作重复出现时保留各自条目。新增、删除最后一组、撤销删除和修改排序都与会话版本一起保存，另一端版本过期时先保留输入，再读取并处理冲突。训练后模式的「保存」确认当前完整有效的非空组；逐组模式只确认用户点击「记下」的组，其他未确认输入需先确认、保留草稿或移除，不能静默计入实际组。删除后的撤销需要当前设备还保有原组完整快照，普通跨端详情不包含已删除数据；快照不可用时不能承诺原组直接撤销。尚未确认的空白或半填草稿不能冒充已完成组；其跨端同步须作为独立草稿能力实现，不能由已确认组接口推定已经支持。

| 异常 | 系统行为与恢复 |
|---|---|
| 模板下架/版本不可访问 | 不能新另存；已有私人历史按安全策略保留，不偷偷换内容 |
| 重复点击/请求超时 | 正式 API 使用同一 clientEventId / recordKey 和版本重放；两种 UI 模式不产生两套数据 |
| 离线 | 已缓存有效快照可记并标「待同步」；未缓存内容明确不可用。本地样机只有本机草稿 |
| 412 版本冲突 | 保留本地输入，按稳定组 ID 合并；同组冲突由用户明确选择，处理前不能完成提交 |
| 登录过期 | 本机草稿保留，重新登录核验主体后续传，不能把旧数据写给另一主体 |
| 存储失败 | 不显示成功，保留当前输入，允许同记录重试 |

实现边界：当前 API 的 /me/training-starts 仍承担「采用计划/安排」原子事务；不能为训练后记录调用它以伪造训练开始。补记走既有会话日期规则。与双模式的正式映射及当前契约缺口见 [集成规则](design/round-04/INTEGRATION.md)。

## F02 日期如何确定

计划内容和执行安排分离。一份私人计划可有多个历史安排，每人最多一个当前训练安排。饮食计划不会占用训练安排。

| 情景 | 唯一规则 |
|---|---|
| 起点 | anchorDate 对应内容 weekIndex=1、dayIndex=1；日期 = anchor + (week-1)×7 + (day-1) |
| 周中开始 | App 让所选训练日对应今天，反推 anchor；effectiveFrom=今天。此前内容不生成漏练义务 |
| 可训练时间 | 已有偏好用于建议首日/选择现成适合的模板，不暗改冻结内容频次。用户可改未开始事项日期 |
| rest 或未列出的日 | 视为休息，不进入计划日完成率分母；不把稀疏数组位置当星期 |
| 漏练 | 当地日期结束且未开始/完成，记 missed；保持原日期，不自动顺延 |
| 暂停 | 从暂停日起未开始项标 paused；暂停天不提醒、不进入分母。正在进行的会话仍可完成 |
| 恢复 | 只恢复当前及未来未开始项。过去暂停项不变，不补成漏练；周期已过则提示重新安排 |
| 改期/跳过 | 仅尚未开始的 scheduled/未来 paused 项；一次只改一个事项。目标不能早于今天或与现有训练冲突；保留 originalDate |
| 换计划/采用新版 | 明示取消旧未来事项；CAS 比较 selectionVersion，原子新建安排。已经发生的会话、原日期和内容版不动 |
| 时区改变 | 安排时区固定。设备出差不改变归日；主动迁移相当于新安排，历史不重算 |
| 离线补录 | date 是实际训练日；occurrenceId 指原应练事项，保留 scheduledDate。逾期完成设 completedLate，审计保留曾漏练状态 |
| 单日/重复会话 | 每事项只有一个非跳过的有效会话；重放恢复同会话。额外练习按自由/临时训练，不重复计完成率 |
| 安排到期 | 无未来项且所有进行中活动处理完时 completed；首页显示周期结束，不强造下一周期 |

**统计口径**：完成率分母为观察窗内已到期、非 rest/paused/cancelled 的事项（skipped 算计划未执行）；分子为这些事项中已完成数，逾期完成单列。按期率仅算在原 scheduledDate 完成。教练「连续 2 个计划日未完成」按最近两个已到期应练事项判断，不是自然连续两天；暂停/未授权/无安排均不触发。定时任务与首页使用同一日历服务，异步提醒发送前重新检查权限和状态。

## F03 教练继续工作，而非重新填表

1. 工作台按待处理原因排优先级，默认接续未完成草稿或待回复学员。仅在有效关系与相应授权下展示证据；没有权限显示「学员尚未授权」，不能推断没有记录。
2. `GET /coach/relations/{id}/plans` 找到草稿，`GET /coach/plans/{id}` 读最新头、publishedVersion、editable。重新进入或更换设备都从服务器恢复。
3. 教练手填或让 AI 起草。ready 必含可审阅的完整内容与动作快照；needs_input 只问缺项；safety_block 给原因和可用的非生成路径。技术故障使用独立错误，不创建空计划。
4. 保存草稿产生新版本；编辑已交付计划时学员继续看到原 publishedVersion。412 时保留本地差异，读取最新头再处理冲突。
5. 教练看到本次具体改动与提示，明确确认后发布。按钮描述「发布给学员」，不写「AI 已批准」。学员收到站内通知，选择启用/采用新版，原安排不被自动替换。
6. 教练点评可关联训练/计划；普通询问与督促走 F04。AI 文案必须先审阅，不能生成即发送。

**动作预算**：从待办到原草稿 ≤2 次导航；一次明确发布确认；相同学员信息重复录入 0。不能用批量自动勾选替代健康授权与内容确认。

## F04 双方能继续说话

有效服务关系双方可发文字，不要求有咨询单、计划或训练。消息独立于通知。发送成功以服务器确认与稳定 ID 为准；失败保留编辑框、同键重试；无网络标待发送，不显示已送达。未读按用户读取游标推进，拒绝微信订阅不影响站内收发。

普通安排消息不要求健康授权。引用健康证据或发送健康类内容要显式分类并检查 scopes；服务端补充敏感分类/引用权限，无法可靠判断时走受限处理，不以客户端普通标签作为放行证明。通知仅「有新消息」，不复制正文。

关系结束后停止发送；双方按已批准的留存配置查看普通历史。撤权后教练的健康消息/附件/摘要变为不可见占位，不回显原文；学员可查看自己仍拥有的内容。缓存隔离按用户/关系/授权版本；撤权事件与重新读取都能失效缓存。已经合法看过的内容无法靠技术抹去人的记忆，告知中需说明撤回影响未来访问。

**未核定项**：普通历史、审计、健康内容各自的具体留存天数和删除例外，由 L01 核定后配置；没有生产配置不开放公开试点，不以无限保留代替决定。

## F05 找到陌生教练并确认服务

1. 学员从教练详情发起咨询，当前教练/套餐自动带入；目标、水平、时间从本人档案预填，只核对变更，预算与备注可省略。
2. 站内咨询沟通需求与服务说明，未读保留，拒绝订阅时仍可回站查看。没有达成服务可关闭咨询并说明原因；从历史再次联系创建新咨询，不复活过期的同意。
3. **后续联系能力由 L01 的平台证据决定**：候选为平台批准的联络组件/方式；只有实际主体、类目、具体入口和内容经核定才允许启用。通过后在咨询内提供「继续联系」入口，双方主动操作，记录授权范围、渠道版本和投递结果。不能把平台客服自动当作教练个人沟通通道。
4. 对未核定、用户拒绝或渠道不可用，明确显示「暂无法完成后续联系」，保留咨询；不展示未经核定的个人微信号、二维码、外部支付链接，也不虚假显示已成交。公开陌生获客开关保持关闭。
5. 实际在允许的渠道达成平台外约定后，教练发起服务说明；学员核对同一 termsHash/版本并确认。成交自报单列，不代表平台验证支付，也不自动授权健康数据。

**完成 R06 的外部验收**：L01 留下官方答复/提审证据和渠道双端脚本；V02 用两名此前不认识、没有联系方式的测试参与者实测以上路径。当前只能完成渠道门槛与异常设计，不能凭文档认定这一链路已经可用。已有私域学员只验证交付，不证明新增获客。

## F06 让 AI 调整已有模板

仅本人 self/template 私人副本可提出调整；教练交付计划中的改动交给教练审核。输入简短意图，App 带入当前 baseVersion；AI 给范围内的建议和差异、缺项或阻断原因。用户核对具体方案后，以 baseVersion + proposalHash + 明确 acknowledged 应用为新版本；过期/版本冲突需重新建议，不自动合并。重试或重复确认不产生两版。新内容不会自动改变已启用的执行安排。

## F07 发布与饮食记录

发布使用已有完整内容或描述预填，集中呈现「缺什么、哪些是估算、将公开什么」，用户确认当前草稿后进入审核。改字段、来源或可见性使旧确认失效。下架立即停止新访问与分享，保留必要审计。

饮食打卡只表达自评；可选观察与估算字段明确区分。没有证据时显示「信息不足」，不展示假摄入统计；不把未打卡当未进食。发布与饮食完整异常覆盖由 B02/B03/B04 交付。

## 三端身份与恢复

微信小程序首批使用微信登录；iOS/Android App 的首个可安装测试版按 D30 使用真实邮箱验证码，正式手机号方向保留。用户需要跨端同步时主动关联，由服务端稳定主体承载权限和数据。小程序先注册：登录后验证并关联测试邮箱，App 验证邮箱和设备持有证明后，由已登录的小程序或其他原有可信会话核对并批准该 App 新设备；App 先注册：从已登录 App 发起配对，在小程序证明微信身份并由原主体核对确认，之后用新的微信 code 登录。两个身份已属于不同主体时不自动合并，保留各自数据并说明当前不能直接关联。以后关联手机号也须本人证明和明确确认。取消、过期、注销后重登和切换账号均不能串数据。

两种训练记录方式在不同端仍指向同一会话与稳定记录键。离线队列绑定主体、资源和版本；未同步与已保存状态分开，重新提交幂等，跨端同组冲突保留输入并交用户处理。撤权后任何端的旧缓存不能继续授予访问。用户在 U08 找到注销入口并确认本人操作，可查看处理中、完成或可恢复失败；A01 负责请求与会话失效，O03 负责删除、留存及备份恢复限制，具体规则按 K01-03 和 L01-03 的合同与证据实施。

### 手机登录、新设备与恢复

测试版邮箱码只证明当前邮箱接收能力，不自动证明旧主体本人；首次登录未占用邮箱时登记设备公钥，已有主体的新设备必须由近期重新认证的可信会话批准，或同时验证本人此前保存并启用的恢复码与新设备签名。测试版先支持无空白、无显示名的 ASCII 邮箱并验证语法；不支持的地址应明确提示。地址重发、次数限制和单次消费按挑战与用途隔离；邮箱和验证码不写日志。邮箱身份可由小程序会话验证后明确关联，若已归属其他主体则拒绝合并。QQ 邮箱是否实际允许本项目发信、邮件能否送达及设备安全存储仍须实测。

手机号验证码证明当前号码可接收短信，不证明号码历史持有人。App 首次为未占用号码创建主体时登记设备公钥；已有主体从未登记的新设备登录时，短信验证后不返回私有数据或完整会话，需在该主体已有的可信 App 会话或已关联小程序微信会话中近期重新认证、核对本次匹配码并明确批准。设备私钥由各平台安全存储生成且不导出；真实能力与备份迁移限制由 P02/A01 验证。无可用可信会话时，若本人已保存并启用备用恢复码，可在短信验证后输入该码，并由新设备证明持有密钥后恢复；恢复码仅能成功使用一次，完成后提醒重新生成。码不可用或原手机号无法接收短信时走人工申诉兜底；实际人工渠道和审核流程仍待建立，不能用短信单因素绕过。

关联时用户保留原任务：一端已认证并近期重新认证，另一端完成当前事务绑定的短信或微信验证，发起端核对匹配码再确认；冲突或取消不合并已有训练、健康资料、关系或授权。解绑须保留至少一个可用登录方式并撤销相应会话；换号只能由当前主体安全验证新号码后生效，旧号码立即失效。当前是合同目标，短信供应商资质、费用、真实设备、恢复和权限均尚未实现或验收。

在恢复码未启用且其他途径不可用时，撤销可信设备或选择退出全部会话并撤销所有设备，如果这样会让本人失去最后一条独立可用的可信登录路径，系统拒绝并说明原因；用户仍可选择只退出会话。普通退出清理当前账号的会话令牌，但不自动删除未撤销的设备密钥。若换号操作使当前会话失效，用户用新号码及原可信设备重新登录；失败时原号码仍有效。设备遗失或被盗后的应急冻结和找回尚需补齐，不能暗示已有服务。

用户在已关联本人手机号或测试邮箱的可信会话设置备用恢复码时，系统只展示一次并提醒安全保存，由本人明确确认已保存后启用。两者均未关联时先完成关联；用户可以稍后设置，但在此之前说明无法使用恢复码自助找回。重新生成时，旧码在新码被确认保存前仍有效；输入错误、取消、过期或网络失败不得让旧码失效。恢复成功后旧码失效，系统提示再次设置。人工申诉是必要兜底，须在上线前建立真实渠道、授权、证据处理、审核及反馈流程；若尚未建立，明确告知未开通而非伪造受理。
